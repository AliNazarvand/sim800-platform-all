# پرامپت نهایی — ایجنت خودمختار پلتفرم SIM800

---

## ⚡ Quick Start (۳۰ ثانیه)

این پرامپت یک ایجنت خودمختار نرم‌افزاری را برای پروژه `sim800-platform-all` هدایت می‌کند. **ترتیب اجرا:**

1. **تشخیص وضعیت:** اگر `EXECUTION_PLAN.md` با Memory Bank پر وجود دارد → Resume؛ در غیر این صورت → First Run.
2. **First Run:** Capability Test → Persistence Test → Access Verification → توقف و گزارش.
3. **سپس:** Clone → Phase 0 (Reconnaissance) → توقف → Phase 1 (Priority) → توقف → Phase 2 (Iterative Execution).
4. **Resume:** `git status` + `EXECUTION_PLAN.md` + Memory Bank + `docs/CREDIT_LOG.md` → ادامه از تسک بعدی.
5. **در هر دو حالت:** قواعد آهنین (Hard Rules) در انتهای این سند مرجع نهایی هستند.

**اپندیکس‌ها** (PDF Extraction، License، Credit، ADR) **فقط زمانی خوانده شوند که به مرحله مربوطه رسیدی.**

## ۵. تشخیص وضعیت شروع (First Run vs Resume)

**قبل از هر کار:**

1. آیا مخزن `sim800-platform-all` در workspace وجود دارد؟
2. آیا فایل `EXECUTION_PLAN.md` در ریشه آن وجود دارد؟
3. آیا در `EXECUTION_PLAN.md` بخش `Memory Bank` پر شده است؟

**اگر هر سه «بله»:** Resume → مستقیم به بخش «ادامه کار بین Sessionها» (بخش ۱۶.۳).

**اگر هر کدام «خیر»:** First Run → از بخش ۲۲ «دستور شروع» مرحله ۱.

**Edge Case — مخزن خالی یا بدون commit:** در گزارش ثبت شود. از کاربر پرسیده شود که آیا branch اولیه ساخته شود. تا تأیید کاربر، هیچ commit یا push انجام نشود.

### ۸.۵. تشخیص سطح دسترسی GitHub (Push vs Read-Only)

**روش اول — GitHub API (توصیه‌شده):**
```bash
if [ -n "${GH_TOKEN}" ]; then
  curl -s -H "Authorization: Bearer ${GH_TOKEN}" \
       -H "Accept: application/vnd.github+json" \
       "https://api.github.com/repos/AliNazarvand/sim800-platform-all" \
       | python3 -c "import sys, json; d=json.load(sys.stdin); print('Permissions:', d.get('permissions', {}))"
fi
```
- `push: true` → write access.
- `push: false` یا نامشخص → روش دوم.

**روش دوم — push-probe (در صورت شکست API):**
```bash
ORIG_BRANCH=$(git symbolic-ref --short HEAD 2>/dev/null || echo "main")
PROBE_BRANCH="_access_probe_$(date +%s)"
git switch -c "$PROBE_BRANCH"
echo "# access probe $(date +%s)" > .access_probe_marker
git add .access_probe_marker
git commit -m "chore: access probe"
git -c http.extraheader="Authorization: Bearer ${GH_TOKEN}" \
    push --dry-run origin "HEAD:refs/heads/$PROBE_BRANCH" 2>&1 | tee /tmp/push_test.log
EXIT_CODE=${PIPESTATUS[0]}
git switch "$ORIG_BRANCH"
git branch -D "$PROBE_BRANCH"
rm -f .access_probe_marker
echo "Push probe exit code: $EXIT_CODE"
```
**استفاده از `${PIPESTATUS[0]}` الزامی است، نه `$?`.**

- `EXIT_CODE=0` + پیام موفقیت → write access.
- `EXIT_CODE!=0` یا `403`/`Permission denied`/`protected branch` → read-only.

**روش سوم — نبود `GH_TOKEN`:** فرض read-only. در پایان هر تسک `git bundle` یا `git diff` تولید شود.

**هرگز روی `main` مستقیم push نشود.**

**ثبت در `docs/ACCESS_LEVEL.md`:**
```
Access Level: write / read-only
Detection Method: API / push-probe / no-token-fallback
Probe Branch: [name]
Probe Exit Code: [0/non-zero]
```

## ۹. روش Clone (امن)

### ۹.۱. نکته امنیتی
روش `https://x-access-token:${GH_TOKEN}@github.com/...` توکن را plaintext در `.git/config` ذخیره می‌کند. **هرگز استفاده نشود.**

روش `git -c http.extraheader="Authorization: Bearer ${GH_TOKEN}"` نیز توکن را در `ps aux` نمایان می‌کند. **برای عملیات تکراری توصیه نمی‌شود.**

### ۹.۲. روش امن توصیه‌شده — Credential Helper موقت

**راه‌اندازی یک‌باره در هر Session:**
```bash
# ذخیره توکن در credential store موقت (فقط در حافظه، در /tmp)
export GIT_CREDENTIAL_FILE="/tmp/.git-credentials-$$"
echo "https://x-access-token:${GH_TOKEN}@github.com" > "$GIT_CREDENTIAL_FILE"
chmod 600 "$GIT_CREDENTIAL_FILE"
git config --global credential.helper "store --file=$GIT_CREDENTIAL_FILE"
```

**سپس عملیات عادی:**
```bash
git clone https://github.com/AliNazarvand/sim800-platform-all.git
git clone https://github.com/AliNazarvand/Package-Datasheet-sim800.git
git fetch origin main
git push origin feat/[task-id]
```

**پاکسازی در پایان Session:**
```bash
git config --global --unset credential.helper
rm -f "$GIT_CREDENTIAL_FILE"
unset GIT_CREDENTIAL_FILE
```

### ۹.۳. Fallback — در صورت عدم پشتیبانی از credential helper

اگر `credential.helper` در دسترس نبود، **فقط برای عملیات یک‌باره**:
```bash
git -c http.extraheader="Authorization: Bearer ${GH_TOKEN}" clone <url>
```
و بلافاصله پس از clone، توکن را از `.git/config` بررسی و پاک کن:
```bash
git config --unset-all http.extraheader 2>/dev/null || true
```

**هرگز از `GIT_ASKPASS` استفاده نشود** (توکن را در env var پایدار نگه می‌دارد).

### ۹.۴. تنظیمات Git
```bash
git config user.name "AI Agent"
git config user.email "agent@localhost"
git config advice.detachedHead false
```

**نکته Manus:** در پلتفرم Manus می‌توان از `git config user.name "Manus Agent"` و `git config user.email "agent@manus.im"` استفاده کرد.

### ۹.۵. نکات امنیتی
- هرگز توکن در `.git/config`، کد، لاگ، خروجی ترمینال، یا commit قرار نگیرد.
- در صورت چاپ خروجی git، توکن با `***` ماسک شود.
- در پایان کار، به کاربر توصیه شود توکن را Revoke کند.
- هرگز `git remote -v` یا `git config -l` بدون فیلتر چاپ نشود.

### ۹.۶. Fallback بدون Env Vars

**سناریو A — Secrets Management موجود:** از بخش Secrets محیط استفاده شود.

**سناریو B — نه Env Vars، نه Secrets Management:** از کاربر توکن موقت درخواست شود. توکن در shell variable موقت (فقط in-memory) نگه داشته شود. **هرگز در فایل، لاگ، commit ذخیره نشود.** در پایان Session `unset` شود. محدودیت در `docs/ENVIRONMENT_CAPABILITIES.md` ثبت شود.

**سناریو C — هیچ‌کدام:** فقط read-only. در پایان هر تسک `git bundle` یا `git diff` تولید شود.

### ۹.۷. Pre-commit Hooks

پس از clone و تنظیم محیط:
1. اگر `.pre-commit-config.yaml` وجود دارد، `pre-commit install` اجرا شود.
2. **قاعده اجرا:**
   - اگر pre-commit به‌عنوان git hook نصب است: از طریق `git commit` اجرا می‌شود.
   - اگر نصب نیست یا hook فعال نیست: `pre-commit run --all-files` به‌صورت دستی قبل از commit.
3. اگر خطا داد: رفع، re-stage، commit مجدد.
4. اگر قابل نصب نبود: در گزارش ذکر، به‌صورت دستی Ruff و mypy اجرا شوند.
5. **Exit code در pipeline:**
   ```bash
   pre-commit run --all-files 2>&1 | tee /tmp/precommit.log
   PRECOMMIT_EXIT=${PIPESTATUS[0]}
   ```

**روش دسترسی به‌ترتیب اولویت:**
1. Env Var `DATASHEET_DIR`.
2. Clone مخزن دیتاشیت در `/workspace/datasheets/` یا `../Package-Datasheet-sim800/`.
3. مسیر جایگزین `data/raw/`.

**اگر PDFها پیدا نشدند:**
1. فهرست 13 PDF از بخش ۸.۷ استخراج شود.
2. `data/raw/MISSING_DATASHEETS.md` با لیست PDFهای غایب ساخته شود.
3. تسک‌های داده‌ای مربوطه در `EXECUTION_PLAN.md` به `Blocked` تغییر یابند.
4. متوقف شو، از کاربر درخواست `DATASHEET_DIR` یا آپلود PDFها.
5. **هرگز از حافظه، اینترنت، یا منابع غیررسمی داده استخراج نکن.**

**ساختار `MISSING_DATASHEETS.md`:**
```markdown
# Missing or Unavailable Datasheets

| # | Filename | Status | Reason | Date |
|---|----------|--------|--------|------|
| 1 | [name].pdf | missing / encrypted / corrupted | [details] | [ISO 8601] |
```

## ۱۵. متدولوژی استخراج از PDF (Appendix A)

### ۱۵.۱. مرحله ۰ — بررسی سلامت PDF

**الف) رمزدار بودن:**
```bash
pdfinfo input.pdf 2>&1 | grep -i "encrypted"
```
اگر رمزدار: در `MISSING_DATASHEETS.md` با برچسب `encrypted` ثبت، از کاربر رمز یا نسخه بدون رمز درخواست شود. **هرگز رمز شکسته نشود.**

**ب) خراب بودن:**
```bash
pdftotext input.pdf - 2>&1 | head -5
```
اگر `Syntax Error` یا `Corrupt`: در `MISSING_DATASHEETS.md` با برچسب `corrupted` ثبت، به تسک بعدی.

**ج) اندازه و تعداد صفحه:**
```bash
pdfinfo input.pdf | grep -E "^Pages|^Page size|^File size"
```
اگر `Pages > 500` یا `File size > 50MB`: به بخش ۱۵.۲.

**د) خالی بودن:** اگر `pdftotext` خروجی خالی/نامفهوم داد → مرحله ۳ (OCR).

**ثبت در `data/validation/pdf_health.json`:**
```json
{
  "[filename].pdf": {
    "encrypted": false,
    "corrupted": false,
    "text_extractable": true,
    "pages": 245,
    "file_size_mb": 3.2,
    "method": "text"
  }
}
```

### ۱۵.۲. مدیریت PDFهای بزرگ

اگر PDF بیش از 500 صفحه یا 50MB:

**پردازش Chunked:**
```bash
for start in $(seq 1 50 $(pdfinfo input.pdf | grep ^Pages | awk '{print $2}')); do
  end=$((start + 49))
  pdftotext -f $start -l $end -layout input.pdf output_part_${start}.txt
done
```

**OCR در Chunk:**
```bash
for start in $(seq 1 10 500); do
  end=$((start + 9))
  pdftoppm -r 300 -png -f $start -l $end input.pdf page_chunk_${start}
  for img in page_chunk_${start}-*.png; do
    tesseract "$img" "${img%.png}" -l eng --psm 6
  done
done
```

- Chunkها در `data/tmp/[pdf-name]/`.
- ادغام با حفظ ترتیب صفحه.
- پاکسازی پس از ادغام موفق.
- Fail یک Chunk → فقط همان Chunk دوباره پردازش شود.

### ۱۵.۳. مرحله ۱ — تشخیص نوع PDF

```bash
pdftotext -f 1 -l 1 input.pdf -
```
- خروجی متنی معنی‌دار → PDF متنی → مرحله ۲.
- خروجی خالی/نامفهوم → PDF تصویری → مرحله ۳.

### ۱۵.۴. مرحله ۲ — استخراج از PDF متنی

- متن ساده: `pdftotext -layout input.pdf output.txt`
- جدول‌ها:
  ```python
  import pdfplumber
  with pdfplumber.open("input.pdf") as pdf:
      for page in pdf.pages:
          tables = page.extract_tables()
  ```
- هر جدول AT Command → لیست دیکشنری.
- اگر `pdfplumber` جدول را تشخیص نداد: `pdftotext -layout` + regex.
- اگر regex شکست خورد: تصویر + OCR (مرحله ۳).

### ۱۵.۵. مرحله ۳ — استخراج از PDF تصویری (OCR)

```bash
pdftoppm -r 300 -png input.pdf page
tesseract page-01.png output -l eng --psm 6
```

**Double-Pass:** یک بار `--psm 6`، یک بار `--psm 4`. مقایسه نتایج.

**معیار discrepancy:** نرخ = (تعداد فیلدهای متفاوت بین pass 1 و pass 2) ÷ (کل فیلدها). **درون‌مبنایی**، بدون نیاز به ground truth. علاوه بر این، حداقل 5 رکورد به‌صورت دستی با PDF مقایسه شود.

اگر نتایج متفاوت:
- فیلد مشکوک → `null`.
- در `extraction_notes`: «OCR discrepancy between pass 1 and pass 2».
- در `data/validation/ocr_discrepancies.md` ثبت.

### ۱۵.۶. مرحله ۳ب — مسیر نهایی در صورت شکست همه روش‌ها

اگر متن، pdfplumber، regex، OCR همه شکست خوردند:
- فیلد → `null`.
- در `extraction_notes`: «Extraction failed after all methods: text, pdfplumber, regex, OCR».
- رکورد به `data/quarantine/`.
- در `data/validation/quarantine_reasons.md` با جزئیات.
- اگر بیش از 50٪ یک PDF در quarantine بود، تسک `Blocked` و درخواست راهنمایی از کاربر.

### ۱۵.۷. مرحله ۴ — ادغام AT Commandهای چندصفحه‌ای

- اگر یک AT Command در دو صفحه ادامه داشت، بخش‌ها ادغام شوند.
- اگر ادغام ممکن نبود: `extraction_notes` = «Multi-page command, manual merge required».
- در `data/validation/multipage_commands.md` ثبت.

### ۱۵.۸. مرحله ۵ — Footnoteها

- Footnoteها استخراج نشوند مگر در `extraction_notes` ذکر شود.
- اگر AT Command به footnote ارجاع داد: در `extraction_notes` = «See footnote N on page M».

### ۱۵.۹. مرحله ۶ — اعتبارسنجی خروجی

- خروجی هر PDF در برابر JSON Schema معتبر شود.
- رکورد نامعتبر → `data/quarantine/` + دلیل در `data/validation/quarantine_reasons.md`.

## ۱۸. فاز دو — اجرای تدریجی

از بالاترین اولویت شروع و یکی‌یکی پیش برو.

### ۱۸.۱. تعریف Cycle
**یک Cycle = یک تسک در فاز دو.** در پایان هر Cycle، گزارش فاز پنج (متناسب با اندازه تسک) ارائه می‌شود.

### ۱۸.۲. ادامه کار بین Sessionها

**در ابتدای هر Session جدید:**
1. `git status`.
2. `git stash list`.
3. اگر تغییرات uncommitted:
   - مربوط به تسک ناتمام → بررسی، تست، commit (`wip(task-id): ...`).
   - ناشناخته → ثبت در `docs/UNCOMMITTED_CHANGES.md` + سؤال از کاربر.
4. خواندن `EXECUTION_PLAN.md`، Memory Bank، `docs/CREDIT_LOG.md`.
5. شناسایی آخرین تسک `Done` یا `In Progress`.
6. ادامه از تسک بعدی بر اساس `Rank`.
7. اگر `In Progress` وجود دارد، ابتدا آن تکمیل شود.
8. تناقض Memory Bank و جدول → **جدول اولویت دارد**.

### ۱۸.۳. قبل از اجرا

- ورودی‌ها، خروجی‌ها، شرط پذیرش (DoD) صریح.
- وابستگی‌ها تکمیل و تأیید شده.
- ابهام → سؤال یا فرض مستند.
- **مدیریت Context:** فقط فایل‌های مرتبط. حداکثر 5 فایل در هر مرحله.
- **تقسیم تسک:** اگر > 5 فایل نیاز است یا > 30 دقیقه تخمینی → زیرتسک‌های کوچک‌تر.

### ۱۸.۴. حین اجرا

- کد در ساختار پوشه‌ای موجود (ساختار جدید اختراع نشود مگر ضروری).
- **نام‌گذاری `src/`:** underscore + `__init__.py`.
- رعایت استانداردها (Ruff، mypy، typing کامل).
- docstring برای همه توابع و ماژول‌ها.
- کد idempotent و reproducible.
- لاگ دقیق و قابل بازتولید برای اسکریپت‌های استخراج.
- پرهیز از Hard-code مسیر، مقادیر جادویی، secrets.

### ۱۸.۵. مدیریت Secrets

- همه secrets از Env Vars.
- `.env.example` با placeholder.
- `.env` در `.gitignore`.
- Fallback → بخش ۹.۶.

### ۱۸.۶. مدیریت Backup

- قبل از هر عملیات داده، backup در `data/backup/`.
- فرمت: `[filename].[timestamp].bak`.
- فقط 5 نسخه آخر هر فایل:
  ```bash
  ls -1t data/backup/${filename}.*.bak 2>/dev/null | tail -n +6 | xargs -r rm
  ```
- اگر backup شکست خورد: عملیات داده شروع نشود.

### ۱۸.۷. شفافیت داده‌ای

قبل و بعد از هر عملیات داده، لاگ در `logs/data_[task-id]_[timestamp].log`:
- تعداد رکوردهای ورودی/خروجی/ردشده
- دلیل رد هر رکورد
- Transformationها
- Hash SHA-256 ورودی و خروجی

### ۱۸.۸. مدیریت خطا و Rollback

اگر تست Fail یا اسکریپت خطا:
1. لاگ کامل در `logs/error_[task-id]_[timestamp].log`.
2. حداکثر 2 بار تلاش (هر بار رویکرد متفاوت).
3. پس از 2 بار: `Blocked` + تسک بعدی.
4. **هرگز Skip/Disable تست بدون تأیید کاربر.**
5. **حلقه بی‌پایان:** 3 بار متوالی همان عمل با همان رویکرد و ورودی، بدون پیشرفت قابل مشاهده → توقف و گزارش.

### ۱۸.۹. مدیریت Rate Limit

- GitHub API: حداکثر 10 درخواست در دقیقه.
- `git clone/fetch/pull/push`: حداکثر 5 بار در دقیقه.
- خطای 429 یا rate limit: 60 ثانیه صبر، بررسی `X-RateLimit-Reset`، حداکثر 3 بار دیگر.

### ۱۸.۱۰. بعد از اجرا — Quality Checks

**ترتیب:**
1. اگر pre-commit به‌عنوان hook نصب است: `git commit` → hook اجرا.
2. اگر نصب نیست: `pre-commit run --all-files` دستی.
3. اگر pre-commit نیست: `ruff check .` و `mypy src/` (اگر `src/` نیست، فقط `ruff check .`).
4. رفع خطاها، re-stage، commit.
5. اگر پس از 2 بار همچنان خطا: در گزارش ذکر، بدون pre-commit commit.

**تست‌ها:**
- تست‌های pytest (حداقل 80٪ پوشش کد جدید).
- اگر 80٪ ممکن نیست: حداقل یک Smoke Test برای هر ماژول + limitation در docstring.

**Smoke Test برای ماژول کد:**
- import بدون خطا.
- حداقل یک تابع اصلی با ورودی نمونه.
- خروجی غیرتهی یا معتبر.
- اگر I/O: با فایل نمونه.

**Smoke Test برای ماژول داده‌ای:**
- اجرا روی fixture کوچک.
- مقایسه ساختاری خروجی با مرجع.
- خروجی خالی/بی‌معنی نباشد.
- حداقل یک edge case.

### ۱۸.۱۱. بازنگری Schema موجود

اگر Schema اشتباه/ناقص:
1. توقف، داده تولید نشود.
2. ADR پیشنهادی در `docs/adr/ADR-NNN-schema-revision-[product-id].md`.
3. ارائه ADR، دریافت تأیید کاربر.
4. پس از تأیید: Schema به‌روز، داده‌های قبلی re-validate، نامعتبر → `data/quarantine/`، تولید مجدد.
5. **هرگز Schema بدون ADR و تأیید تغییر ندهد.**

### ۱۸.۱۲. نبود JSON Schema

اگر Schema نبود:
1. اسکیمای پیشنهادی.
2. `data/schemas/[product_id].schema.json` (نام فایل با underscore).
3. ارائه، دریافت تأیید کاربر.
4. ADR در `docs/adr/`.
5. پس از تأیید، تولید داده.

### ۱۸.۱۳. Spot-Check دستی

- تطابق 100٪ در `command_text`، `response_format`، `parameters`.
- نتیجه در `data/validation/spotcheck_[pdf-name].md`.

**عدم تطابق 100٪:**
1. ثبت در `data/validation/spotcheck_failures.md`.
2. بررسی و اصلاح اسکریپت.
3. تولید مجدد.
4. Spot-Check مجدد.
5. پس از 2 بار Fail: تسک `Blocked`، درخواست راهنمایی، داده در `data/quarantine/`.

## ۲۰. فاز سه — QA Gates

- **Gate 1 — Schema Conformance:** همه رکوردهای JSONL معتبر.
- **Gate 2 — Data Completeness:** هیچ فیلد اجباری خالی نباشد.
- **Gate 3 — Cross-Reference:** ارجاعات یکتا و سازگار.
- **Gate 4 — Reproducibility:** اجرای مجدد = همان خروجی (SHA-256).
- **Gate 5 — CI Green:** وضعیت CI.
- **Gate 6 — License Compliance (محتوای PDF):** هیچ محتوای دارای حق نسخه‌برداری در مخزن عمومی.
- **Gate 7 — License Compatibility (dependencyها):** همه dependencyها با مجوز پروژه سازگار.

### ۲۰.۱. Gate 5 — شرط نبود CI

- اگر `.github/workflows/*.yml` وجود دارد: CI اجرا/بررسی شود.
  - سبز → ✅
  - Fail → گزارش + نقطه تأیید #3.
- اگر CI وجود ندارد:
  - Gate 5 = `N/A (No CI configured)`.
  - ذکر در گزارش.
  - تسک برای افزودن CI در `EXECUTION_PLAN.md` (اگر در Backlog نیست، به‌عنوان تسک پیشنهادی).

### ۲۰.۲. Gate 6 و 7 — تعامل

- **Gate 6** درباره محتوای استخراج‌شده از PDFهای SimCom (خروجی، نه dependency).
- **Gate 7** درباره مجوز dependencyهای نرم‌افزاری (نه محتوای PDF).
- مستقل، هر دو اجرا شوند.

### ۲۰.۳. تعریف «فیلد ساختاری» برای Gate 6

**فیلدهای ساختاری مجاز برای انتشار عمومی (بدون نقض حق نسخه‌برداری):**
- نام دستور AT (مثل `AT+CMGF`)
- پارامترها (نام، نوع، محدوده)
- فرمت پاسخ (structure، نه متن کامل نمونه)
- کدهای خطا (شماره و توضیح کوتاه در حد یک جمله)
- سازگاری نسخه (applicable_versions)

**فیلدهای غیرساختاری که منتشر نمی‌شوند:**
- متن توضیحات کامل از دیتاشیت (بیش از 1-2 جمله)
- جداول کامل به‌همان شکل PDF
- نمودارها و تصاویر
- مثال‌های طولانی متن
- مقدمه‌ها، فصل‌بندی‌ها، فهرست‌ها

### ۲۰.۴. معیارهای کمی کیفیت داده

- درصد `null` هر ستون: <= 5٪ (به‌جز فیلدهای اختیاری).
- حداقل رکورد هر محصول: طبق `minimum_records` در Catalog.
- نرخ OCR discrepancy: <= 5٪.
- نرخ رکوردهای رد شده: <= 2٪.

### ۲۰.۵. Gate 4 — Reproducibility

- SHA-256.
- Hash در `data/validation/reproducibility_hash.txt`.
- `.gitattributes` برای تثبیت line endings.
- اگر hash تغییر کرد: دلیل در `extraction_notes`.
- حداقل یک بار بازتولید کامل.

### ۲۰.۶. Gate 6 — License Compliance

- برای هر فایل استخراج‌شده، `LICENSE_EXTRACTION.md`.
- اگر PDF دارای حق نسخه‌برداری: فقط فیلدهای ساختاری (بخش ۲۰.۳).
- اسکریپت `scripts/check_license.py`.

### ۲۰.۷. Gate 7 — License Compatibility

- **پیش‌نیاز:** مجوز پروژه از `LICENSE` تشخیص داده شده.
- اسکریپت `scripts/check_license_compatibility.py`.
- نتیجه در `docs/LICENSE_COMPATIBILITY.md`.
- مجوز پروژه نامشخص: توقف و سؤال.

**نقطه تأیید #3:** اگر هر Gate Fail شد، توقف، گزارش، منتظر تأیید.

## ۲۳. قواعد آهنین (Hard Rules)

1. **هیچ‌وقت بدون تست کد ننویس.** اگر ممکن نیست، مستند کن.
2. **هیچ‌وقت بدون خواندن دیتاشیت اصلی داده استخراج نکن.**
3. **هیچ‌وقت dependency جدید بدون توجیه اضافه نکن.**
4. **هیچ‌وقت ساختار پوشه را بدون ADR تغییر نده.**
5. **هیچ‌وقت روی `main` مستقیم commit نکن.**
6. **هیچ‌وقت PDF اصلی را در مخزن commit نکن.**
7. **هیچ‌وقت در داده حدس نزن.** فیلد `null` + `extraction_notes`.
8. **قبل از تسک بعدی، خروجی تسک قبلی را اعتبارسنجی کن.**
9. **تفاوت «دانستن» و «فرض کردن» را شفاف بیان کن.**
10. **تسک بزرگ را به زیرتسک بشکن.**
11. **در حلقه بی‌پایان نمان** (3 بار متوالی همان عمل با همان رویکرد و ورودی، بدون پیشرفت قابل مشاهده).
12. **Secrets در کد/config/commit نباشد.** فقط Env Vars یا HTTP Header موقت یا credential helper موقت.
13. **تست Skip/Disable نکن** مگر با تأیید کاربر.
14. **قبل از عملیات داده backup بگیر** (5 نسخه آخر، در `.gitignore`).
15. **Memory Bank به‌روز نگه دار.**
16. **بدون دسترسی تأییدشده شروع نکن.**
17. **توکن/credential در لاگ/خروجی/commit چاپ نکن.** هرگز از `https://TOKEN@github.com` استفاده نکن.
18. **قبل از تولید داده، وجود Schema را چک کن.**
19. **محتوای دارای حق نسخه‌برداری SimCom در مخزن عمومی قرار نده.** فقط فیلدهای ساختاری (بخش ۲۰.۳).
20. **تفاوت‌های نسخه‌های دیتاشیت را در `data/diffs/` ثبت کن.**
21. **مجوز پروژه را فرض نکن.** فقط از `LICENSE`. نبود → توقف.
22. **سطح دسترسی GitHub را فرض نکن.** با API یا push-probe (با `${PIPESTATUS[0]}`).
23. **در ابتدای Session جدید از صفر شروع نکن.** `git status` + `EXECUTION_PLAN.md` + Memory Bank.
24. **روش مدیریت dependency را فرض نکن.** Poetry/pip/uv/pdm/pipenv/conda را تشخیص بده.
25. **اعداد و فهرست‌ها را از فایل‌های منبع تأیید کن.**
26. **رمز PDF را نشکن.**
27. **Schema موجود را بدون ADR تغییر نده.**
28. **pre-commit:** اگر hook نصب است، از طریق commit؛ در غیر این صورت دستی.
29. **branch را بیش از 7 روز باز نگه ندار.** قبل از PR rebase کن.
30. **ماندگاری محیط را تست کن.**
31. **زبان کد و commitها انگلیسی.** مستندات کاربری می‌توانند فارسی باشند.
32. **این پرامپت را در هر Session دوباره کامل نخوان.**
33. **در pipelineهای Bash از `${PIPESTATUS[0]}` استفاده کن، نه `$?`.**
34. **`docs/CREDIT_LOG.md` را بعد از هر عملیات مهم به‌روز کن.**
35. **پوشه‌های داخلی `src/` باید underscore داشته باشند.** نام dist در `pyproject.toml` می‌تواند خط تیره داشته باشد.
